## 1. なぜこの区別が必要か

この検証環境は、本番（Oracle 12c・RAC・5TB・500表）を**単一ホスト上の Oracle 21c XE コンテナ2台**で
模したものです。データ量は数十MB、対象は3表です。

そのため、ここで得られた結果には性質の違う3種類が混ざります。

| 種別 | 意味 | そのまま本番に持ち込めるか |
|---|---|---|
| ✅ **検証済み** | この環境で実際に動かし、結果を確認した事実 | **手順・ロジックは持ち込める。** ただし規模・構成に依存する数値は持ち込めない |
| 🟡 **仮決定** | 本来は社内で検討して決めるべきだが、検証を進めるため暫定で置いた値 | **持ち込めない。** 社内で決め直すこと |
| 🔴 **本番未検証** | この環境では再現できず、確認できていない事項 | **持ち込めない。** 本番相当環境での確認が必要 |

**最も避けたい事故**は、🟡の仮決定値が「検証済みの推奨値」として本番設計に流れ込むことです。
そのため、仮決定には必ず「**本来の決め方**（誰が何を根拠に決めるか）」を併記しています。

## 3. 記法のルール（今後この文書群に追記する人向け）

本文中では、次の形式で印を付けます。**新しく書く人も必ずこの形式に従ってください。**

### 3.1 仮決定

```markdown
> 🟡 **仮決定 TMP-06** — Data Pump ジョブ分割は2ジョブ（GRP01/GRP02）とした。
> **なぜ仮か**: 検証データが3表しかなく、分割設計の妥当性を評価できないため。
> **本来の決め方**: 対象500表の容量・依存関係・並列度・所要時間見積りから、社内の移行設計担当が決定する。
> **参照**: 設計メモ §3.3 P1-09 / §10 Step5
```

必須4要素は **決めた内容 / なぜ仮か / 本来の決め方（誰が・何を根拠に）/ 参照先** です。
「なぜ仮か」を省くと、後任者が「検証の結果こうなった」と誤読します。

### 3.2 本番未検証

```markdown
> 🔴 **本番未検証 UNV-01** — RAC の Thread 別挙動は確認していない。
> **なぜ**: oracle-src はシングルインスタンスのため。
> **本番で必要な確認**: 全 Thread の Archived Redo が漏れなく収集されること、Thread 別 Sequence の管理。
> **参照**: 設計メモ §2.1.2 / §5.2.4
```

### 3.3 検証済み

```markdown
> ✅ **検証済み** — 全物理コピーが VERIFIED になるまで論理ログを VERIFIED にしないこと。
> **根拠**: `scripts/62_test_migration_ctl_e2e.sh` T11（2026-07-27 実行、PASS）
```

**根拠には必ず「どのスクリプトで」「いつ」を書きます。** 書けないものは検証済みではありません。

## 5. 本番未検証台帳（🔴 本番相当環境で確認すること）

### 5.1 この環境の制約で再現できなかったもの

| ID | 未検証事項 | なぜ再現できないか | 本番で必要な確認 |
|---|---|---|---|
| **UNV-01** | RAC の Thread 別挙動 | `oracle-src` はシングルインスタンス | 全 Thread の Archived Redo が漏れなく収集されること、Thread 別 Sequence 管理、`MIG_CHECKPOINT` の Thread 別保持 |
| **UNV-02** | 5TB / 500表 規模の実測値 | 検証データは数十MB / 3表 | 所要時間・並列度・ダンプ分割数・UNDO/TEMP 消費・ネットワーク帯域。**ジョブ分割設計（TMP-06）の前提になる** |
| **UNV-03** | 8TB SSD 搬送方式 | 物理媒体がない | 直接書込み性能・取外し搬送・接続後のチェックサム照合・RAC 環境での DIRECTORY 制約 |
| **UNV-04** | Oracle 12c / 19c の実バージョン差 | 両側とも 21c XE | 12.1/12.2 差、19c 固有挙動、プラットフォーム互換性 |
| **UNV-05** | 独立した物理ファイルサーバ | 単一ホスト上の共有ボリュームで代替 | NFS/CIFS マウント方式・帯域・障害時の再取得・容量設計 |
| **UNV-06** | 新設計フェーズ4（移行先でLogMiner実行）の本格検証 | PoC は**1表に1回 UPDATE しただけ**の規模。手動操作 | INSERT/DELETE、複合主キー、BLOB/CLOB、複数トランザクション、CSF分割行の再構成、追付き性能 |
| **UNV-07** | フェーズ1・2（Data Pump Export/Import）の本番相当検証 | 規模・媒体・ファイルサーバがいずれも異なる | 上記 UNV-02/03/05 とセットで実施 |
| **UNV-08** | 文字コード・各国語設定 | 検証環境は単一の文字セット | 移行元・移行先の NLS 設定差と変換影響 |

### 5.2 社内で「詳細再調査の対象外」と決めているもの

設計メモ §12.2 が**現行方針上の除外事項**として明示している項目です。
**この検証でやっていないのは意図的であり、抜け漏れではありません。**
ただし方針が変われば調査対象に戻ります。

- Oracle 12c の 12.1／12.2 差による方式再検討
- プラットフォーム互換性の再検討
- 文字コード・各国語設定の**方式**再検討（※差分の確認自体は UNV-08 として残る）
- 主キー・複合主キーの全件詳細棚卸し
- テーブル変換パターン自体の再分類
- テーブルごとの DML 種別調査
- Supplemental Logging の負荷増加の詳細検証
- DDL 凍結可否
- LogMiner Unsupported 操作の網羅調査
- 1万件単位 COMMIT の再検討

## 10. この文書の保守ルール

- 仮決定を**追加**したら §4 に ID 付きで追記する。本文にだけ書いて台帳に載せないことを禁止する
